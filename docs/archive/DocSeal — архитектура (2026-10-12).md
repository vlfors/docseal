# DocSeal — архитектура

Oct 12, 2026 · @Vladimir

## 1. Цели и границы

DocSeal (рабочее название) — открытая библиотека, CLI и веб-верификатор, которые доказывают три факта о документе или пакете документов: **целостность** (байты не изменились), **время** (существовал не позже момента T) и **авторство** (подписан владельцем ключа K). В блокчейн попадает только Merkle-корень, сами документы никогда не покидают устройство пользователя без его воли.

**Что система доказывает**

- Целостность каждого файла и всего пакета (SHA-256 + Merkle-дерево).
- Существование не позже времени блока (якорь в блокчейне или метка RFC 3161).
- Что пакет подписан конкретным ключом (подпись над корнем манифеста).

**Что система не доказывает**

- Что владелец ключа — конкретное физическое или юридическое лицо: это задача PKI (сертификаты X.509, eIDAS, КЭП) или внешней верификации личности.
- Юридическую значимость сама по себе: якорь в блокчейне — доказательство целостности и времени, а не квалифицированная подпись.
- Что документ не существовал раньше T или что содержимое истинно.

**Ключевые принципы**

1. Hash-only: в публичные сети уходят только хеши, без имён файлов и метаданных.
2. Self-contained proof: пакет доказательств проверяется без нашего сервера, достаточно файла и публичного блокчейна.
3. Plugin-first: подпись и якорение — интерфейсы с несколькими реализациями, ядро от них не зависит.
4. Crypto-agility: алгоритм хеша и подписи указан в данных, их можно менять без поломки старых пакетов.

## 3. Нефункциональные требования (NFR)

Главное NFR — проверка без нас: любой, у кого есть пакет и доступ к публичному блокчейну, получает тот же вердикт, даже если проект закрыт.

| ID | Категория | Требование |
| --- | --- | --- |
| NFR-01 | Независимость | Проверка работает офлайн (кроме сверки с блокчейном) и не требует нашего сервера; формат пакета открыт и описан спецификацией |
| NFR-02 | Приватность | Документы не покидают устройство; в блокчейн уходит только корень; в публичном логе нет имён файлов и метаданных |
| NFR-03 | Безопасность | Только аудированные криптобиблиотеки (`@noble/*`, WebCrypto); никакой самописной криптографии, кроме сборки Merkle-дерева |
| NFR-04 | Долговечность | Пакет проверяем через 20+ лет: версионированная схема, алгоритмы указаны явно, возможна повторная заякорка (re-timestamping) при ослаблении алгоритма |
| NFR-05 | Детерминизм | Одни и те же файлы дают один и тот же корень на любой ОС и в любом рантайме; покрыто тестовыми векторами |
| NFR-06 | Производительность | Потоковое хеширование: файл 2 ГБ в браузере без загрузки целиком в память; 10 000 файлов в пакете |
| NFR-07 | Стоимость | Режим по умолчанию бесплатен (OpenTimestamps); платные сети опциональны и батчатся |
| NFR-08 | Расширяемость | Новый алгоритм подписи или сеть якорения добавляется отдельным npm-пакетом без изменения ядра |
| NFR-09 | Переносимость | Ядро работает в браузере, Node.js, Deno, Bun; CLI собирается в один бинарь |
| NFR-10 | Совместимость | Версия формата в манифесте; новые версии читают старые пакеты; неизвестные поля игнорируются, неизвестный `alg` даёт вердикт «не поддерживается», а не ошибку |
| NFR-11 | Качество | Покрытие ядра тестами 90%+, fuzz-тесты парсера пакета, воспроизводимые сборки, подписанные релизы |
| NFR-12 | Лицензия | Apache-2.0 (патентная оговорка важна для криптографии) |

## 4. Компонентная архитектура

Архитектура из четырёх слоёв: клиенты вызывают ядро, ядро работает только через четыре интерфейса, а плагины этих интерфейсов — единственное место, где код касается ключей, PKI и блокчейнов.

_(диаграмма утеряна при экспорте; см. ARCHITECTURE.md)_

Новая сеть или алгоритм подписи — это новый npm-пакет в третьем ряду; ядро и клиенты при этом не меняются. Сервер необязателен: подпись и проверка работают без него.

## 5. Расширяемость подписи

Подпись разделена на три независимых интерфейса: `SignatureSuite` (алгоритм: подписать и проверить байты), `KeyProvider` (где живёт закрытый ключ) и `TrustPolicy` (кому верить). Так Ed25519 из файла, тот же Ed25519 на YubiKey и ГОСТ через КриптоПро подключаются одинаково, а решение «доверять ли ключу» не смешивается с математикой.

```typescript
// packages/core/src/signature.ts
export interface SignatureSuite {
  readonly id: string;            // "ed25519", "ecdsa-p256", "x509-cms", "gost-2012-256"
  readonly specVersion: 1;
  /** Только проверка: чистая функция, обязана работать в браузере */
  verify(env: SignatureEnvelope, payload: Uint8Array): Promise<CryptoVerdict>;
}

export interface KeyProvider {
  readonly suite: string;         // с каким SignatureSuite совместим
  getSigner(): Promise<SignerIdentity>;          // публичный ключ / сертификат
  sign(payload: Uint8Array): Promise<Uint8Array>; // ключ может быть в HSM и не покидать его
}

export interface TrustPolicy {
  evaluate(signer: SignerIdentity, at: Date | null): Promise<TrustVerdict>;
}

export interface SignatureEnvelope {
  suite: string;                  // "ed25519"
  signer: SignerIdentity;         // { kind: "did:key" | "x509" | "pgp" | "webauthn", id, chain? }
  role?: "author" | "approver" | "witness" | string;
  claimedAt: string;              // время по часам подписанта, не доказательство
  signedAttrs: Record<string, unknown>;
  value: string;                  // base64url
}
```

**Что именно подписывается.** Не корень напрямую, а байты с разделением доменов: `"DocSeal/v1/sig\0" || SHA-256(JCS(manifest)) || SHA-256(JCS(signedAttrs))`. Префикс не даёт переиспользовать подпись в другом протоколе, а хеш манифеста закрывает и корень, и метаданные.

**Регистрация плагинов** — явная, без динамической загрузки по имени из пакета (иначе чужой пакет мог бы подсунуть «верификатор», который всегда отвечает «да»):

```typescript
import { DocSeal } from "@docseal/core";
import { ed25519 } from "@docseal/sig-ed25519";
import { openTimestamps } from "@docseal/anchor-ots";

const ds = new DocSeal({
  signatures: [ed25519()],
  anchors: [openTimestamps({ calendars: ["https://a.pool.opentimestamps.org"] })],
  trust: pinnedKeys(["did:key:z6Mk…"]),
});
```

**Неизвестный алгоритм** при проверке даёт вердикт `unsupported` для этой подписи, а не падение всей проверки: остальные подписи и якоря проверяются как обычно.

**Планируемые плагины подписи**

| Пакет | Где ключ | Юридическая значимость | Этап |
| --- | --- | --- | --- |
| `sig-ed25519` | файл, WebCrypto (неизвлекаемый ключ) | нет, техническая подпись | MVP |
| `sig-webauthn` | passkey, YubiKey | нет | 2 |
| `sig-x509-cms` | PKCS#12, PKCS#11 (HSM, токены) | eIDAS AdES/QES при квалифицированном сертификате | 3 |
| `sig-openpgp` | GnuPG | нет | 3 |
| `sig-gost` | КриптоПро CSP / Рутокен через локальный агент | КЭП по 63-ФЗ | 4 |
| `sig-sigstore` | без долгоживущего ключа, вход через OIDC | нет | 4 |

## 6. Расширяемость якорения

Якорение — интерфейс `AnchorProvider` с тремя операциями: отправить хеш, дотянуть доказательство, проверить его. Чтение блокчейна при проверке вынесено в отдельный `ChainReader`, чтобы проверяющий сам выбирал, кому доверять: своему узлу, публичному explorer или нескольким сразу.

```typescript
// packages/core/src/anchor.ts
export interface AnchorProvider {
  readonly id: string;                 // "ots", "eas", "rfc3161", "rekor"
  submit(digest: Uint8Array): Promise<AnchorReceipt>;           // может вернуть pending
  upgrade?(r: AnchorReceipt): Promise<AnchorReceipt>;           // pending → confirmed
  verify(r: AnchorReceipt, digest: Uint8Array, chain: ChainReader): Promise<AnchorVerdict>;
}

export interface AnchorReceipt {
  provider: string;                    // "ots"
  network: string;                     // CAIP-2: "bip122:000000000019d6689c085ae165831e93", "eip155:8453"
  status: "pending" | "confirmed" | "failed";
  digest: string;                      // что заякорено (hex)
  proof: string;                       // формат провайдера, base64 (.ots, receipt транзакции, TST)
  locator?: { tx?: string; block?: number; logIndex?: number };
  submittedAt: string;
}

export interface AnchorVerdict {
  valid: boolean;
  status: "confirmed" | "pending" | "invalid" | "unsupported";
  attestedTime?: string;               // время блока или TSA: это и есть доказанное время
  confirmations?: number;
}

export interface ChainReader {
  bitcoinBlockHeader?(height: number): Promise<{ merkleRoot: string; time: number }>;
  evmLog?(chainId: number, tx: string, logIndex: number): Promise<{ data: string; blockTime: number }>;
}
```

**Что якорится.** Не голый корень, а «печать» после подписей: `seal = SHA-256("DocSeal/v1/anchor\0" || SHA-256(JCS(manifest)) || SHA-256(подписи по порядку))`. Так время доказано и для подписей. Это нужно для отзыва ключей: подпись, заякоренная до отзыва, остаётся действительной. Если позже добавился подписант, создаётся новая печать и новый якорь, старые сохраняются.

**Жизненный цикл.** `submit` → `pending` (у OpenTimestamps это обещание календаря) → `upgrade` → `confirmed` (есть путь до заголовка блока). `failed` — провайдер отказал или истёк срок; тогда пакет можно заякорить заново другим провайдером. Через годы при ослаблении SHA-256 пакет переякоривают новым алгоритмом поверх старого доказательства (re-timestamping).

**Батчинг** — обёртка `batched(provider, { maxItems, maxWaitSec })` над любым провайдером: собирает печати многих пакетов, строит Merkle-дерево, отправляет один корень. Каждый пакет получает квитанцию «путь до корня батча + квитанция провайдера». Для OpenTimestamps это не нужно, календари батчат сами; для EVM это главный способ снизить стоимость.

**Несколько якорей сразу.** Пакет может содержать квитанции разных провайдеров на одну печать: например, OpenTimestamps (бесплатно, надёжно, но часы) + RFC 3161 (секунды, юридически понятная метка времени). Вердикт по времени — самое раннее подтверждённое `attestedTime`.

**Планируемые провайдеры**

| Пакет | Сеть | Стоимость | Подтверждение | Этап |
| --- | --- | --- | --- | --- |
| `anchor-ots` | Bitcoin через календари OpenTimestamps | бесплатно | часы | MVP |
| `anchor-rfc3161` | TSA (бесплатная или квалифицированная по eIDAS) | бесплатно / платно | секунды | 2 |
| `anchor-evm` | любая EVM-сеть, минимальный контракт с событием `Anchored(bytes32)` | газ, с батчингом мало | секунды–минуты | 3 |
| `anchor-eas` | EVM L2 через Ethereum Attestation Service | газ | секунды–минуты | 3 |
| `anchor-rekor` | журнал прозрачности Sigstore Rekor (не блокчейн) | бесплатно | секунды | 4 |

Для EVM-контракта — только событие, без записи в storage: событие в разы дешевле, а логи доступны через любой RPC.

## 7. Модель данных

В исходный пример манифеста стоит добавить: идентификатор пакета, описание правила Merkle-дерева, тип и соль файла, ссылку на предыдущую версию, метаданные, политику подписей и генератор. Без явного правила дерева другой реализации не воспроизвести корень.

**manifest.json** (перед хешированием канонизируется по RFC 8785 JCS; хеши — hex в нижнем регистре)

```json
{
  "$schema": "https://docseal.dev/schema/manifest/v1.json",
  "version": 1,
  "id": "urn:uuid:3b0c4f8e-6a1d-4c2b-9f57-0d1e2a3b4c5d",
  "hashAlg": "sha-256",
  "merkle": {
    "scheme": "docseal-v1",
    "leafOrder": "path-utf8-bytes"
  },
  "files": [
    {
      "path": "annex-1.pdf",
      "size": 50211,
      "mediaType": "application/pdf",
      "hash": "a71b…",
      "salt": "q8W3…"
    },
    {
      "path": "contract.pdf",
      "size": 182344,
      "mediaType": "application/pdf",
      "hash": "9f2c…",
      "salt": "Zt1x…"
    }
  ],
  "merkleRoot": "3e8d…",
  "previous": null,
  "metadata": {
    "title": "Договор поставки № 17/2026",
    "reference": "17/2026",
    "tags": ["contract"],
    "custom": {}
  },
  "signaturePolicy": { "type": "m-of-n", "m": 2, "signers": ["did:key:z6Mk…A", "did:key:z6Mk…B"] },
  "createdAt": "2026-10-11T18:00:00Z",
  "generator": "docseal-cli/0.1.0"
}
```

**Правило дерева `docseal-v1`**

- Лист: `H(0x00 || JCS({path, size, hash, salt}))`. Путь и размер внутри листа, поэтому переименование файла тоже ломает корень.
- Узел: `H(0x01 || left || right)`. Разные префиксы защищают от подмены листа узлом (second-preimage).
- Листья сортируются по байтам UTF-8 пути после NFC-нормализации; непарный узел поднимается вверх без дублирования (как в RFC 6962).
- Соль — 16 случайных байт на файл. Она нужна для выборочного раскрытия: в Merkle-proof видны хеши соседних листьев, и без соли по ним можно подобрать типовой короткий документ.

**signatures/0001.json**

```json
{
  "suite": "ed25519",
  "signer": { "kind": "did:key", "id": "did:key:z6Mk…A" },
  "role": "author",
  "claimedAt": "2026-10-11T18:01:12Z",
  "signedAttrs": { "manifestHash": "c41a…", "purpose": "approve" },
  "value": "mF3k…"
}
```

**anchors/seal-1.json** — печать и квитанции к ней

```json
{
  "seal": "77e0…",
  "inputs": { "manifestHash": "c41a…", "signatures": ["signatures/0001.json", "signatures/0002.json"] },
  "receipts": [
    {
      "provider": "ots",
      "network": "bip122:000000000019d6689c085ae165831e93",
      "status": "confirmed",
      "digest": "77e0…",
      "proof": "AE9wZW5UaW1lc3RhbXBz…",
      "locator": { "block": 915432 },
      "submittedAt": "2026-10-11T18:02:00Z"
    }
  ]
}
```

**Структура пакета** `.dseal` — ZIP по образцу ASiC-E. «Тонкий» пакет без `files/` можно публиковать отдельно от документов; «толстый» — с документами внутри.

```text
contract-17-2026.dseal
├── mimetype                     application/vnd.docseal+zip (первым, без сжатия)
├── manifest.json
├── signatures/
│   ├── 0001.json
│   └── 0002.json
├── anchors/
│   └── seal-1.json              печать + квитанции всех провайдеров
├── proofs/                      (опц.) Merkle-proof каждого файла для выборочного раскрытия
│   └── contract.pdf.proof.json
└── files/                       (опц.) сами документы
    ├── annex-1.pdf
    └── contract.pdf
```

Все схемы публикуются как JSON Schema в `spec/` и версионируются вместе с полем `version`.

### Паспорт пакета (FR-20)

Паспорт — аналог почтовой описи вложения: он показывает, **из чего** состоит пакет, кем подписан и когда заякорен, но не раскрывает содержимое документов. Он доказывает состав пакета, а не подлинность каждого документа: подлинность конкретного файла проверяется сверкой его хеша с паспортом и Merkle-proof.

**Свойства**

- Производный артефакт: генерируется детерминированно из `manifest.json`, подписей и квитанций, внутрь пакета не входит (иначе возникла бы циклическая зависимость хешей).
- Самопроверяемый: `passport.json` содержит `manifestHash` и `seal`; верификатор пересобирает паспорт из пакета и сравнивает. Подделанный паспорт не совпадёт с подписанным манифестом.
- Режим маскировки: имена файлов можно скрыть (`№ 1, № 2…`), оставив только размеры и хеши, если сами названия конфиденциальны.
- Три представления: `passport.json` для машин, `passport.pdf` для людей, QR-код на PDF со ссылкой на веб-верификатор и `seal`.
- На этапе 3 PDF можно подписать PAdES-подписью (плагин `sig-x509-cms`), чтобы он сам по себе имел юридический вес.

**Что в паспорте**

| Блок | Поля |
| --- | --- |
| Пакет | название, `id`, дата создания, версия, ссылка на предыдущую версию |
| Состав | № · имя файла (или маска) · тип · размер · SHA-256 · соль не показывается |
| Целостность | `merkleRoot`, `manifestHash`, `seal` |
| Подписанты | имя или идентификатор, роль, алгоритм, отпечаток ключа или сертификата, заявленное время |
| Якоря | провайдер, сеть, блок или транзакция, доказанное время, статус |
| Проверка | QR и ссылка на верификатор, краткая инструкция |
| Оговорка | фиксированный текст: «Паспорт подтверждает состав пакета. Подлинность документа подтверждается совпадением его SHA-256 с хешем в паспорте и проверкой Merkle-proof» |

**passport.json**

```json
{
  "type": "docseal-passport",
  "version": 1,
  "package": { "id": "urn:uuid:3b0c4f8e-…", "title": "Договор поставки № 17/2026", "createdAt": "2026-10-11T18:00:00Z" },
  "masked": false,
  "files": [
    { "n": 1, "path": "annex-1.pdf", "mediaType": "application/pdf", "size": 50211, "hash": "a71b…" },
    { "n": 2, "path": "contract.pdf", "mediaType": "application/pdf", "size": 182344, "hash": "9f2c…" }
  ],
  "integrity": { "merkleRoot": "3e8d…", "manifestHash": "c41a…", "seal": "77e0…" },
  "signers": [
    { "id": "did:key:z6Mk…A", "role": "author", "suite": "ed25519", "claimedAt": "2026-10-11T18:01:12Z" }
  ],
  "anchors": [
    { "provider": "ots", "network": "bitcoin", "block": 915432, "attestedTime": "2026-10-11T21:14:05Z", "status": "confirmed" }

```

**Сценарий использования.** Сторона получает паспорт по почте и видит состав пакета. Позже у неё на руках оказывается `contract.pdf`: она перетаскивает файл в веб-верификатор (или сканирует QR), хеш совпадает со строкой № 2, Merkle-proof сходится с корнем — вердикт «Файл contract.pdf подлинный и входит в пакет 17/2026» (`PARTIAL`). Вердикт `VALID` для всего пакета паспорт не выдаёт никогда.

CLI: `docseal passport contract-17.dseal -o passport.pdf [--mask-names] [--json passport.json]`.

## 8. Потоки и проверка

Подпись и якорение выполняются на устройстве пользователя; сервер нужен только для батчинга и фонового `upgrade`. Проверка — детерминированный конвейер из шести шагов, каждый шаг даёт свой вердикт, итог собирается из них.

**Создание пакета**

1. Потоково хешировать каждый файл (SHA-256), сгенерировать соль на файл.
2. Собрать манифест, канонизировать JCS, вычислить `manifestHash` и Merkle-корень.
3. Каждый подписант через свой `KeyProvider` подписывает байты из раздела 5 и получает `SignatureEnvelope`.
4. Вычислить печать (раздел 6) и отправить её всем настроенным `AnchorProvider` — квитанции в статусе `pending`.
5. Записать `.dseal`; при желании выдать Merkle-proof для каждого файла.
6. Позже `docseal upgrade` (или фоновый воркер сервера) переводит квитанции в `confirmed`.

**Второй подписант** получает пакет, проверяет его, добавляет свою подпись и создаёт новую печать `seal-2` со своим якорем. Старые подписи и печати не меняются, поэтому история согласования видна и доказуема.

**Проверка пакета**

1. Формат: `mimetype`, версия схемы, валидность JSON Schema.
2. Файлы: каждый файл из манифеста хешируется и сравнивается; отсутствующий, изменённый и лишний файл различаются.
3. Корень: листья и Merkle-корень пересчитываются и сравниваются с `merkleRoot`.
4. Подписи: `SignatureSuite.verify` для каждой, затем `TrustPolicy.evaluate`, затем проверка `signaturePolicy` (например, 2 из 2).
5. Якоря: печать пересчитывается из `inputs`, каждая квитанция проверяется через `ChainReader`; берётся самое раннее подтверждённое время.
6. Ключи: если ключ отозван, подпись засчитывается только при подтверждённом якоре раньше даты отзыва.

**Проверка одного файла** (выборочное раскрытие): хеш файла + `path`, `size`, `salt` из proof дают лист, путь до корня даёт корень, корень сверяется с подписанным манифестом. Остальные файлы при этом не нужны.

**Итоговые вердикты**

| Вердикт | Когда |
| --- | --- |
| `VALID` | Все файлы целы, корень совпал, политика подписей выполнена доверенными ключами, есть хотя бы один подтверждённый якорь |
| `VALID_PENDING` | Всё как в `VALID`, но якоря ещё в статусе `pending`: время пока не доказано |
| `VALID_UNTRUSTED` | Криптография сошлась, но подписант не входит в политику доверия проверяющего |
| `PARTIAL` | Проверены только раскрытые файлы (выборочное раскрытие) или часть подписей с неподдерживаемым алгоритмом |
| `INVALID` | Файл изменён или отсутствует, корень не совпал, подпись неверна или якорь не сходится с блокчейном |

Отчёт машиночитаемый: на каждый шаг — статус, причина и ссылки на доказательства (номер блока, транзакция, сертификат), чтобы его можно было приложить к спору.

## 9. Модель угроз

Самые опасные угрозы — не взлом SHA-256, а подмена верификатора и путаница «подписано» с «подписано тем, кем надо». Поэтому ядро, проверка и политика доверия отделены, а веб-верификатор распространяется так, чтобы его можно было собрать и сверить самому.

| Угроза | Мера |
| --- | --- |
| Изменён байт в документе | Хеш файла и Merkle-корень не сходятся → `INVALID` |
| Подменён файл с пересчётом манифеста | Подпись над `manifestHash` перестаёт сходиться |
| Переименован или переставлен файл | Путь и размер входят в лист дерева |
| Подмена листа узлом (second-preimage) | Префиксы `0x00` / `0x01` для листьев и узлов |
| Подбор короткого документа по хешу из Merkle-proof | Соль на файл |
| Подпись «задним числом» украденным ключом | Время доказывает только якорь; подпись после отзыва без более раннего якоря не засчитывается |
| Злой верификатор, всегда отвечающий «да» | Явная регистрация плагинов, подписанные релизы, воспроизводимая сборка, верификатор открыт и запускается локально |
| Подменённый explorer блокчейна | `ChainReader` настраивается; можно свой узел или сверку с несколькими источниками |
| Отказ календаря OpenTimestamps или TSA | Несколько календарей и провайдеров на одну печать |
| Ослабление SHA-256 через годы | Crypto-agility в формате и переякорение новым алгоритмом поверх старого доказательства |
| Утечка метаданных через публичную сеть | В сеть уходит только 32-байтная печать |
| Ключ подписанта не принадлежит заявленному лицу | Вне ядра: `TrustPolicy`, X.509/eIDAS/КЭП, закреплённые ключи |
| Атаки на парсер ZIP (zip bomb, `../` в путях) | Лимиты размеров, запрет абсолютных путей и `..`, fuzz-тесты |
| Проверка одного файла (в том числе служебного) выдаётся за проверку всего пакета | Отдельный вердикт PARTIAL с именем проверенного файла; VALID только после проверки всех файлов; фиксированная оговорка в паспорте пакета |

## 10. Стек, интерфейсы, этапы

Выбран TypeScript-монорепо: один и тот же код ядра работает в браузере (проверка без загрузки файлов), в Node.js (CLI, сервер) и в SDK. Rust + WASM — запасной путь, если упрёмся в производительность.

| Слой | Технологии |
| --- | --- |
| Монорепо | pnpm workspaces, Turborepo, TypeScript strict, tsup |
| Криптография | `@noble/hashes`, `@noble/curves`, WebCrypto; `pkijs` для X.509/CMS |
| Канонизация | `canonicalize` (RFC 8785 JCS) |
| Контейнер | `fflate` (потоковый ZIP) |
| Якоря | `javascript-opentimestamps`, `viem` (EVM), EAS SDK |
| CLI | Node.js + `commander`, сборка в один бинарь |
| Веб | SvelteKit (статический), Web Workers для хеширования; хостинг GitHub Pages |
| Сервер (опц.) | Hono + PostgreSQL: батчинг, фоновый `upgrade`, индекс хешей, вебхуки |
| Тесты | Vitest, тестовые векторы в `spec/vectors`, fast-check для fuzz |

**Структура репозитория**

```text
docseal/
├── spec/                    формат, JSON Schema, тестовые векторы
├── packages/
│   ├── core/                хеширование, Merkle, манифест, пакет, конвейер проверки, интерфейсы
│   ├── sig-ed25519/
│   ├── sig-webauthn/
│   ├── sig-x509-cms/
│   ├── anchor-ots/
│   ├── anchor-rfc3161/
│   ├── anchor-evm/
│   └── sdk/                 высокоуровневый API для интеграторов
├── apps/
│   ├── cli/
│   ├── web/                 веб-подпись и веб-верификатор
│   └── server/              батчинг, upgrade, индекс
└── contracts/               минимальный EVM-контракт Anchored(bytes32)
```

**CLI**

```bash
docseal keygen --suite ed25519 -o me.key
docseal seal ./contract-17/ --key me.key --anchor ots -o contract-17.dseal
docseal cosign contract-17.dseal --key partner.key --anchor ots
docseal upgrade contract-17.dseal
docseal verify contract-17.dseal --files ./contract-17/ --trust trusted-keys.json --json
docseal prove contract-17.dseal contract.pdf -o contract.pdf.proof.json
```

**Этапы**

1. MVP: спецификация формата v1, `core`, `sig-ed25519`, `anchor-ots`, CLI (`keygen`, `seal`, `upgrade`, `verify`), тестовые векторы.
2. Веб-верификатор в браузере, паспорт пакета, выборочное раскрытие, мультиподпись, версии пакета, соль, `anchor-rfc3161`, `sig-webauthn`.
3. Сервер (батчинг, фоновый `upgrade`, индекс хешей, вебхуки), `anchor-evm` / `anchor-eas`, `sig-x509-cms`, `sig-openpgp`, отзыв ключей, отчёт в PDF.
4. ASiC-E экспорт, `sig-gost`, `anchor-rekor`, `sig-sigstore`, внешний аудит безопасности.
